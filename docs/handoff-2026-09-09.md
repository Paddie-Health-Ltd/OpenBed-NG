## 3. Ward categories — why ten, and what is deliberately not split

`A_AND_E`, `ICU_ADULT`, `ICU_PAEDIATRIC`, `MEDICAL_ADULT`, `PAEDIATRIC`,
`THEATRE`, `SURGICAL`, `MATERNITY`, `NICU`, `SCBU`.

**The kickoff never enumerated these.** It states "all eight categories" as a
Gate 3 contract and names `paediatrician closes NICU/SCBU` as a duty-flag rule,
and lists no values. The set was chosen at implementation time; an audit before
the window closed found two defects in that choice.

- **`ICU` split by age.** Ventilator circuits, tube sizes, drug dosing and nursing
  competency differ. A dispatcher routing a child to a facility showing free ICU
  beds that are adult beds has been handed a false positive — the same defect the
  duty-cover gate exists to prevent. `ICU` was **not** kept to mean adult: a label
  answering a narrower question than the reader asked is the defect being removed.
- **`PAEDIATRIC` added, `GENERAL_MEDICAL` → `MEDICAL_ADULT`.** There was no tile
  at all for a general paediatric admission, which is commoner than a paediatric
  ICU one. Not named `MEDICAL_PAEDIATRIC`: most children's wards take medical
  **and** post-surgical children in one unit, so the narrower name is the same
  defect in the other direction. The asymmetry with `MEDICAL_ADULT` is correct
  because the reality is asymmetric.

**Not split, deliberately:** `THEATRE`, `A_AND_E`, `SURGICAL`, `MATERNITY` are
usually one unit taking both adults and children.

**Recorded residual:** if `PAEDIATRIC` absorbs post-operative children then
`SURGICAL` is now *de facto* adult — the same implicit narrowing one value out.
This cannot be chased to completion by naming, because where wards divide by age
varies by facility. It is clinician question 4.

The male/female medical split stays closed — decided on a **different axis**
(sex, not age), so splitting on age does not reopen it.

**The paediatrician flag now gates four categories** (`NICU`, `SCBU`,
`PAEDIATRIC`, `ICU_PAEDIATRIC`), flagged in both derivation sites as a **default
pending clinician confirmation**. It is transcription of an existing rule, not a
new one. The flag itself is **not** split: most Nigerian tier-2 facilities have no
neonatologist, so a separate neonatal flag would read `UNKNOWN` or `NO`
permanently — a real distinction nobody keeps honest.

## 7. Things that will look wrong and are not

- **`supabase/migrations/` is empty and `[db.migrations] enabled = false`** —
  deliberate. Two runners over one schema corrupts it. `supabase db reset` does
  **not** restore this schema; use `npm run db:reset`.
- **`auto_expose_new_tables = true`** in `supabase/config.toml` — deliberately at
  the cloud default. Hardening it locally would make the RLS negative suite pass
  against a stricter regime than production runs.
- **`[api] max_rows = 1000`** — cloud default on purpose; the 200-row cap is
  enforced in SQL inside the RPCs, and lowering it locally would make the cap test
  pass for the wrong reason.
- **`refusal_note` and `fingerprint` are forbidden column names that exist
  nowhere** — forbidding an absent name catches a *reintroduction*.
- **TypeScript pinned at 5.9.3** — no stable `typescript-eslint` supports TS 7,
  and the duty-flag ESLint rule must actually run.

## 8. OPEN AND UNDIAGNOSED — the `lint_migration_header` ACCEPT-leg intermittent

**Status: not fixed. Cause not found. Do not close this on a green run.**

### What happened

`tests/compliance/lint_migration_header.test.ts > a well-formed plant is
accepted` failed on GitHub Actions at commit `91c7108` (run `34410413362`),
reporting only `AssertionError: expected 1 to be +0`. The lint had exited 1,
which in `scripts/lint_migration_header.sh` can happen **only** when a `FAIL:`
line was printed — so a check genuinely rejected a file. Which file, and which
check, is unknown: the assertion discarded the lint's stdout.

The commit under test added **one file, `docs/handoff-2026-09-09.md`, 209 lines**,
and changed nothing else. The lint's inputs were therefore byte-identical to
commit `f03f066`, where the same job passed.

### The decisive experiment

The job was re-run on the **identical commit, with no changes**. It passed, and
all six required checks went green.

Same commit, same inputs, opposite outcomes. The failure is **nondeterministic**.
That is a finding, not a diagnosis.

### Hypotheses excluded, each by a probe rather than by argument

| Hypothesis | How it was excluded |
|---|---|
| BSD vs GNU userland — the `awk`/`grep`/`printf` in the lint | Ran the lint against the same corpus under `ubuntu:24.04` with **mawk 1.3.4**. PASS. Same class as the earlier `mapfile` bash-3.2 finding, so it was the leading candidate; it is not the cause. |
| bash 3.2 (macOS) vs bash 5.2 (CI) | Same container run, GNU bash 5.2.15. PASS. |
| Divergent corpus between local and CI | `git ls-files database/migrations` = 27, on-disk = 27, and the two lists are identical. Working tree clean; local `HEAD` == `origin/handoff-2026-09-09`. |
| Something in PR #3's diff | `git show --stat` — one docs file, 209 insertions, nothing else. |
| A concurrent test writing into the REAL `database/migrations` | Every write in `tests/compliance/` is rooted at a `withScratch` temp dir, including `audit_log_no_identity_columns.test.ts`'s in-place rewrite, whose `target` is `join(root, MIGRATION)`. |
| A lint script using a fixed-name temp file two workers could share | No script under `scripts/` uses `mktemp`, `/tmp`, `TMPDIR` or `$$` at all. |
| Concurrency across the ten compliance files | Full `--project compliance` run inside the Debian container: **134/134 passed**. The single-file run passed too. |
| SIGPIPE from `printf … \| grep -q` under `pipefail` — `grep -q` exits on first match, and a `pipefail` pipeline reports the writer's 141 | Ruled out by mechanism, not by luck: `grep` cannot exit before data arrives, and every banner in this corpus is far below the 64 KiB pipe buffer, so `printf`'s write completes without blocking. Recorded because it is the right shape of explanation and the next reader will think of it. |

### What was changed, and what it is not

Both legs of the trio that assert **acceptance** now attach the lint's stdout to
the assertion, and the ACCEPT leg additionally prints the scratch directory
listing and the exact bytes written for `900_valid.sql`. That separates the three
states `expected 1 to be +0` cannot: a missing file, a wrong file, or a genuinely
nondeterministic lint.

**This is instrumentation, not a fix.** The next occurrence will name the file
and the check in the CI log. Until then the cause is unknown and this item stays
open.
